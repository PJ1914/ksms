## Phase 6 decisions (2026-11-18)

| ID    | Decision                                                                                                                                                        | Rationale                                                                                         | Status  |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------- |
| TD-44 | Units carry `is_packaging` and `standard_factor` (CHECK: exactly one kind). Standard conversions are derived from them; packaging sizes are per product         | Removes hand-typed factors for kg/g/L/ml (typos corrupt stock); keeps BAG/CAN/CARTON flexible     | Decided |
| TD-45 | Global units are **seeded by a migration** (idempotent `ON CONFLICT DO NOTHING`), not a seed script                                                             | Reference data must exist identically in dev, CI, tests and production                            | Decided |
| TD-46 | Quantities are converted exactly and **never rounded**; results finer than 3 decimals are refused (`QUANTITY_PRECISION`)                                        | A silent rounding would change stock or price                                                     | Decided |
| TD-47 | Price resolution order: exact price point, then unit price x quantity, then base price scaled; round half-up to paise; no price means an error                  | Predictable and explainable to a shopkeeper; never invents a price                                | Decided |
| TD-48 | Product `type` and `baseUnitId` are immutable; a mistaken product with no history is deleted and recreated                                                      | They define the meaning of every stock number; changing them later would silently corrupt history | Decided |
| TD-49 | Products with stock, purchase or sale history cannot be deleted (`PRODUCT_HAS_HISTORY`); use `DISCONTINUED`. Soft delete frees barcodes, keeps the SKU reserved | Business rules 13 and 17                                                                          | Decided |
| TD-50 | Every catalogue change (including prices, conversions, barcodes) bumps `products.version`; edits accept the loaded version (409 on mismatch)                    | Two devices must not overwrite each other, and delta sync sees child changes                      | Decided |
| TD-51 | Domain rule violations use `DomainError` (framework-free) and are returned as HTTP 422 with a stable code                                                       | Keeps business rules testable without Nest                                                        | Decided |
| TD-52 | Added `products.min_sale_increment` (the assumed 50 g step, per product, optional)                                                                              | Needed by POS (Phase 9); the catalogue is where the shop configures it                            | Decided |

## Phase 7 decisions (2026-11-18)

| ID    | Decision                                                                                                                                                                           | Rationale                                                                                                                          | Status  |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------- |
| TD-53 | One inventory engine (`receive` / `issue` / `issueMany`) is the only code that changes stock; it always runs in the caller's transaction                                           | Purchases, sales, returns and adjustments share one tested set of rules; a sale and its stock change are atomic                    | Decided |
| TD-54 | Concurrency: `SELECT ... FOR UPDATE` on the balance row (created on demand with `ON CONFLICT DO NOTHING`), then batch rows in FEFO order; multi-product issues in product-id order | Serialises competing sales in PostgreSQL itself; fixed lock order prevents deadlocks. Proven on Neon's pooled connection (TD-32)   | Decided |
| TD-55 | Moving weighted-average cost at product + branch level, 4 decimals half-up; deficit resets the average to the incoming cost; batch costs kept for information only                 | Single valuation method (spec), simple to reconcile                                                                                | Decided |
| TD-56 | FEFO with expiry evaluated in India time; expired batches are never sold or received; expiry write-offs name the batch                                                             | Food safety and correct valuation                                                                                                  | Decided |
| TD-57 | Generic `IdempotencyService`: key claimed by `INSERT ... ON CONFLICT DO NOTHING` as the first statement of the work's own transaction; response stored in the same commit          | Exactly-once without locks in application memory; concurrent duplicates wait on the unique index and replay; failures free the key | Decided |
| TD-58 | Stock commands require an `Idempotency-Key` UUID header                                                                                                                            | Business rule 15; retried requests on a shaky mobile network must not double-adjust                                                | Decided |
| TD-59 | Cost/value fields in stock views only for `report.inventory` holders                                                                                                               | Cashiers need quantities, not purchase costs                                                                                       | Decided |
| TD-60 | Negative stock: shop setting + `stock.override_negative` + written reason; deficit recorded as an unbatched movement                                                               | Spec: "unless an authorized override is explicitly configured and audited"                                                         | Decided |

## Phase 8 decisions (2026-11-19)

| ID    | Decision                                                                                                                                                                                               | Rationale                                                                                                                                             | Status  |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| TD-65 | A purchase moves DRAFT -> CONFIRMED -> PARTIALLY_RECEIVED -> RECEIVED. Only goods received add stock and what the shop owes; `receiveNow` does create + receive in one transaction                     | Spec: "only received goods increase stock; supplier payable created on receipt"; the walk-in purchase stays one tap                                   | Decided |
| TD-66 | Payable per receipt = cumulative `round(line payable x received / ordered)` minus what was already posted; exact at completion. Round-off settles with the last receipt                                | Partial receipts always add up to the exact total, no lost paise                                                                                      | Decided |
| TD-67 | Freight and other additional costs are shared across lines in proportion to line value (largest remainder to the paisa) and become part of each item's stock cost                                      | Moving average cost then reflects the true landed cost                                                                                                | Decided |
| TD-68 | Purchase GST: GST-registered shop treats input tax as recoverable (not in stock cost); a non-registered shop adds it to cost                                                                           | Standard treatment; needs accountant confirmation before production                                                                                   | Decided |
| TD-69 | Purchase return credit = proportional price paid on the purchase line (cumulative, exact), stock leaves through the inventory engine at current average cost; returns are always against a purchase    | Supplier credit notes are in the purchase price, not today's cost; one rule for partial returns                                                       | Decided |
| TD-70 | Supplier payments allocate to purchases oldest first or as chosen; unmatched money is an advance (negative balance). Mistakes are reversed (opposite payment, cashbook and ledger lines), never edited | Matches how shopkeepers settle bills; history stays append-only                                                                                       | Decided |
| TD-71 | One `SupplierLedgerService` is the only writer of what is owed; supplier lock is always taken LAST (purchase -> stock -> supplier). Locks are `FOR NO KEY UPDATE`                                      | Fixed lock order = no deadlocks; NO KEY UPDATE avoids the foreign-key deadlock between a payment and a receipt (found while reviewing the lock order) | Decided |
| TD-72 | Document numbers (`PUR`, `PRT`, `PV`) come from `document_sequences` with one atomic `UPDATE ... RETURNING` inside the caller's transaction                                                            | Gap-free and unique under concurrency; Phase 9 invoices reuse it                                                                                      | Decided |
| TD-73 | `GET /procurement/reconciliation` proves stock, purchases, returns, payments and supplier balances agree; tests run it after every scenario                                                            | "Atomic stock + payable reconciliation" exit criterion of the roadmap                                                                                 | Decided |
| TD-74 | Dates are validated as real calendar dates (`2026-02-31` is refused with `EXPIRY_INVALID`/`PURCHASE_DATE_INVALID`), including in the inventory engine                                                  | Found in Phase 8: such a date used to reach the database and fail with a 500                                                                          | Decided |
