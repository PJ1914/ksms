# Migration Strategy

Phase 2. Prisma Migrate (SQL migrations checked into `apps/api/prisma/migrations/`).

## Tooling facts (verified 2026-11-17)

- Prisma **7.10.1** (stable). npm's `latest` tag currently points at an 8.0 release candidate; **do not float** — pin exact versions.
- Prisma 7 requires a `prisma.config.ts` (datasource URL lives there, not in the schema). It is created in Phase 3 and points at `prisma/schema`.
- Multi-file schema folder is supported (resolves TD-18).
- Generated client output: `apps/api/src/generated/prisma` (git-ignored, generated in CI/build).

## Workflow

1. Edit `prisma/schema/*.prisma`.
2. `prisma migrate dev --name <change>` against the **dev** Neon branch (uses a shadow database; Neon dev branch or a second branch for shadow).
3. Hand-written SQL (checks/triggers/partial indexes) goes in its own migration so Prisma-generated diffs stay clean. Prisma does not manage these objects; do not drop them in generated migrations.
4. Review SQL in PR. CI runs `prisma validate`, applies all migrations to a clean Postgres, and runs the constraint tests.
5. Deploy: a dedicated job runs `prisma migrate deploy` with the Neon **direct** URL. **Never at app start-up.**

## Reversibility and risk

Prisma has no automatic down-migrations. Policy: each migration PR includes a documented rollback note.

| Migration type                                                                        | Rollback                                                                                                                                    |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Additive (new table/column/index)                                                     | Drop in a follow-up migration                                                                                                               |
| Triggers/checks (0002)                                                                | `DROP TRIGGER … ; ALTER TABLE … DROP CONSTRAINT …` (names are explicit)                                                                     |
| Destructive (drop/rename/type change)                                                 | **Risk**: data loss. Requires expand/contract (add new → backfill → switch code → drop later), a fresh Neon branch backup first, and an ADR |
| Production safety net: Neon point-in-time restore + nightly off-site dump (Phase 17). |

## Test database resets

History tables reject `TRUNCATE`/`DELETE`. Tests must create a fresh schema (`prisma migrate reset` / drop schema) instead of truncating tables.
