# Migration Strategy

Phase 2. Prisma Migrate (SQL migrations checked into `apps/api/prisma/migrations/`).

- Prisma 7 requires a `prisma.config.ts` (datasource URL lives there, not in the schema). It is created in Phase 3 and points at `prisma/schema`.
- Multi-file schema folder is supported (resolves TD-18).
- Generated client output: `apps/api/src/generated/prisma` (git-ignored, generated in CI/build).

## Workflow

1. Edit `prisma/schema/*.prisma`.
2. `prisma migrate dev --name <change>` against the **dev** Neon branch (uses a shadow database; Neon dev branch or a second branch for shadow).
3. Hand-written SQL (checks/triggers/partial indexes) goes in its own migration so Prisma-generated diffs stay clean. Prisma does not manage these objects; do not drop them in generated migrations.
4. Review SQL in PR. CI runs `prisma validate`, applies all migrations to a clean Postgres, and runs the constraint tests.
5. Deploy: a dedicated job runs `prisma migrate deploy` with the Neon **direct** URL. **Never at app start-up.**

## Reversibility and risk

Prisma has no automatic down-migrations. Policy: each migration PR includes a documented rollback note.

| Migration type                                                                        | Rollback                                                                                                                                    |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Additive (new table/column/index)                                                     | Drop in a follow-up migration                                                                                                               |
| Triggers/checks (0002)                                                                | `DROP TRIGGER … ; ALTER TABLE … DROP CONSTRAINT …` (names are explicit)                                                                     |
| Destructive (drop/rename/type change)                                                 | **Risk**: data loss. Requires expand/contract (add new → backfill → switch code → drop later), a fresh Neon branch backup first, and an ADR |
| Production safety net: Neon point-in-time restore + nightly off-site dump (Phase 17). |

## Test database resets

History tables reject `TRUNCATE`/`DELETE`. Tests must create a fresh schema (`prisma migrate reset` / drop schema) instead of truncating tables.

### Creating large indexes on production without blocking writes

`CREATE INDEX` blocks writes to the table while it builds, and `CREATE INDEX CONCURRENTLY` cannot run inside the transaction `prisma migrate deploy` uses. For a big table:

1. Connect with the DIRECT url and run each statement of the migration by hand with `CONCURRENTLY` added, for example `CREATE INDEX CONCURRENTLY IF NOT EXISTS "products_name_trgm_idx" ON "products" USING gin ("name" public.gin_trgm_ops) WHERE "deleted_at" IS NULL;` (same names as the migration).
2. Check none is left `INVALID` (`SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;`); drop and retry any that is.
3. Mark the migration applied without running it: `pnpm --filter @ksms/api exec prisma migrate resolve --applied 20261126000100_search_trigram_indexes`.

With today's data (one shop, a few thousand rows) the plain migration finishes in well under a second, so `prisma migrate deploy` is fine as is.

### Measured effect (F10)

Throwaway schema on the production Neon project, 50,000 products and 20,000 customers in one shop, `EXPLAIN (ANALYZE, BUFFERS)`, selective search text:

| Query                                                                       | Before            | After                                                                 |
| --------------------------------------------------------------------------- | ----------------- | --------------------------------------------------------------------- |
| product name only                                                           | 23.1 ms, Seq Scan | 0.14 ms, Bitmap Index Scan `products_name_trgm_idx`                   |
| product name / local name / SKU                                             | 32.5 ms, Seq Scan | 0.16 ms, BitmapOr over the three trigram indexes                      |
| product list search as the API now sends it (barcode matches fetched first) | 33.7 ms           | 1.2 ms                                                                |
| the old API shape (barcode sub-query inside the OR)                         | 61 ms             | 59 ms: the sub-query blocks the indexes, which is why the API changed |
| 500 product inserts                                                         | 95 ms             | 106 ms (+11 %, within network noise)                                  |

Searches of one or two characters cannot use trigram indexes and fall back to a scan; that is the same cost as before.
