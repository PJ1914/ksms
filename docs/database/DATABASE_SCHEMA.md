# Database Schema Documentation

Phase 2. Prisma 7.10.1 (stable). Schema: `apps/api/prisma/schema/` — one file per domain: `base`, `identity`, `catalog`, `inventory`, `procurement`, `sales`, `finance`, `operations`. 53 tables, validated with `prisma validate`.

## Conventions

| Topic                  | Rule                                                                                                                                 |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Table / column names   | snake_case, plural tables via `@@map` / `@map` (Prisma client uses camelCase)                                                        |
| Primary keys           | `uuid(7)` generated by Prisma (time-ordered, index-friendly), `@db.Uuid`                                                             |
| Money                  | `NUMERIC(14,2)` (max ≈ ₹99,99,99,99,999.99)                                                                                          |
| Quantities             | `NUMERIC(14,3)`, always in **base unit** except line fields explicitly in selling/purchase unit                                      |
| Unit cost              | `NUMERIC(14,4)` per base unit (weighted average needs extra precision)                                                               |
| Tax rate               | `NUMERIC(7,4)` percent (CHECK 0–100)                                                                                                 |
| Conversion factor      | `NUMERIC(18,6)`, CHECK > 0                                                                                                           |
| Timestamps             | `timestamptz(3)` UTC; business dates are `date`                                                                                      |
| Enums                  | Native Postgres enums (explicit status/type values)                                                                                  |
| Soft delete            | `deleted_at` on master data only: organizations, branches, categories, products, customers, suppliers, collection agents, held bills |
| Never deleted          | sales, sale items, invoices, payments, ledgers, cashbook, stock movements, audit logs (DB triggers enforce)                          |
| Optimistic concurrency | `version` on products, customers, suppliers (sync conflict detection)                                                                |

Decimals cross the API as **strings**; code uses `decimal.js`, never `number`.

## Core design decisions

1. **Unit conversion**: every product has one `base_unit_id`. `product_unit_conversions.factor_to_base` says how many base units one of that unit equals _for that product_ (KG product: G = 0.001, BAG = 25). Lines (`sale_items`, `purchase_items`) copy the factor at transaction time, so later edits never change history. Weight and volume are never converted (units carry a `dimension`; services reject mismatches).
2. **Packaged vs loose**: separate SKUs where separately sellable (1 L bottle = COUNT/PCS product; loose oil = VOLUME/L product).
3. **Stock**: `stock_movements` is the append-only truth (signed quantity, cost snapshot, `balance_after`); `inventory_balances` is derived. A CHECK ties movement sign to type.
4. **Negative stock** is blocked by the app's conditional UPDATE. There is intentionally **no** DB CHECK on `quantity_on_hand >= 0` because an audited override may allow it; reconciliation tests cover this instead.
5. **Sales**: `sales.paid_total + credit_amount = total` (CHECK). Credit portion creates a `customer_ledger_entries` row. Cancellation sets `status = CANCELLED` and writes reversing rows.
6. **Invoices**: one per sale, unique number per branch, `(series, sequence_number)` unique; snapshot fields immutable.
7. **Idempotency**: `idempotency_records (organization_id, key)` unique with `request_hash`; same key + different payload → 422.

## Tenant isolation strategy

- Every tenant-owned table carries `organization_id`; branch-operational tables also carry `branch_id`. Global tables: `users`, `permissions`, `units_of_measurement`.
- All repositories require a `TenantContext` and always filter by `organization_id` (and `branch_id` where relevant); controllers never pass raw ids to queries without tenant scope.
- Every composite index leads with `organization_id`.
- Cross-tenant referential integrity (e.g., a sale line pointing at another org's product) is **not** enforced by composite FKs (cost/complexity trade-off). It is covered by service-level validation and mandatory cross-org tests (Phase 5/16). **Future hardening option**: PostgreSQL Row-Level Security keyed on a session setting; not adopted now because Neon pooled connections + Prisma make per-request session settings fragile (ADR when revisited).
- `branch_id` and actor columns (`created_by_id` etc.) have no FK where noted in `ERD.md`; documented trade-off to avoid ~40 extra named relations. Referenced rows are never hard-deleted, so dangling references cannot arise through the app.

## Seed strategy

| Data                                                                          | When                                                                                                                   | How                                                          |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Units of measurement (KG, G, L, ML, PCS, DOZEN, BAG, CARTON, CAN, PACK, BOX…) | Every environment                                                                                                      | Idempotent seed script (upsert by `code`), run by deploy job |
| Permissions catalogue                                                         | Every environment                                                                                                      | Idempotent seed from a code constant in Phase 5              |
| System roles + role permissions                                               | On organization creation                                                                                               | `OrganizationService.create` in one transaction              |
| Default expense categories, cash register "Main Register", document sequences | On branch creation                                                                                                     | Same transaction                                             |
| Demo/test data                                                                | **Never in production**; dev/test only via a separate `seed:dev` script that refuses to run when `NODE_ENV=production` | —                                                            |
